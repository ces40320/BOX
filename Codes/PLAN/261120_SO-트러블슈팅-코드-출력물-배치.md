# SO 트러블슈팅 코드·출력물 배치

- **정리일**: 2026-11-20
- **관련 transcript**: [SO 트러블슈팅 재배치](2329e94b-5d0a-491d-9af0-8d17654bb181)
- **핵심**: SO 실패 대응 코드를 `Codes/c_Run_Tools/troubleshoot_so/` 아래 해결 접근법별로 모으고, 피험자 전용 스크립트를 없앰. 트라이얼 전용 모델·미완성 조각은 SO 결과 폴더의 `troubleshoot_so/<접근법>/`, 그 밖의 진단·상태 파일은 `Analysis/Asymmetric/_diagnosis/`에 둠.

---

## 1. 원칙

- 피험자 전용 `.py`를 만들지 않는다. 대상은 항상 `--namecode / --condition / --seg / --apps` 인자 또는 SO 실패 기록(`pipeline_trouble.json`)에서 고른다.
- 공유 스케일 모델(`SUB#_Scaled.osim`)과 이미 성공한 트라이얼은 덮어쓰지 않는다.
- 최종(정규) SO·JR 결과는 항상 원래 위치(`SO_<app>/`, `JR_<app>/`)에 같은 이름으로 쓴다. 후속 분석 코드는 복구 여부를 몰라도 된다.
- 접근법 이름 세 가지(`rerun_freeze`, `wrap_gapfill`, `wrap_fbp`)를 코드 폴더, SO 결과 하위폴더, `_diagnosis` 하위폴더에서 똑같이 쓴다. 품질 진단은 `diagnosis`(코드) / `quality_check`(출력).

## 2. 접근법별 문제와 해결

| 접근법 | 풀려는 문제 | 방법 |
|---|---|---|
| `rerun_freeze` | SO가 특정 시각에서 멈춤(로그 정지), 또는 시작 직후 실패 | 멈춘 프레임 앞뒤로 나눠 SO 후 이어 붙임 / 0.05 s부터 다시 실행 |
| `wrap_gapfill` | Chest 랩 근육 경로가 짧게 튐(Tier A: 짧은 구간) | 정상 구간만 SO 후 짧은 틈을 3차 보간 |
| `wrap_fbp` | Chest 랩 측면 전환으로 근육 길이가 반복해서 튐(Tier B) | 튀는 근육만 L5_S1 3자유도 다항식 길이 함수(FunctionBasedPath)로 바꾼 트라이얼 전용 모델로 SO·JR |
| (Tier C) | 위 방법으로 고칠 수 없음 | SO를 만들어내지 않고 실패 기록에 주분석 제외 표시 |

## 3. 코드 구조와 이름 규칙

- 직접 실행하는 파일: 첫 단어를 대문자 동작어로 (`RUN_`, `RETRY_`, `DETECT_`, `UPDATE_`).
- 함수만 담은 파일: `<주제>_lib.py`.
- `troubleshoot_so/` 아래 파일은 패키지가 아니라 파일로 실행한다. 각 파일은 `troubleshoot_so/`를 `sys.path`에 넣고 `_ts_paths`를 import해 공식 파이프라인 모듈과 각 접근법 폴더를 모듈 이름만으로 불러온다.

```text
Codes/c_Run_Tools/
  run_opensim_pipeline.py            공식 파이프라인 (트라이얼 모델 자동 선택 포함)
  opensim_pipeline_handlers.py       공식 SO/JR 실행 함수
  pipeline_rules.py                  resolve_model_path(seg=) → 트라이얼 모델이 있으면 그것을 사용
  UPDATE_pipeline_progress.py        진행 시트·실패 기록 갱신
  watch_pipeline_gate.py             완료 감지 후 다음 명령 기동
  troubleshoot_so/
    _ts_paths.py                     import 경로 설정
    wrap_detect_lib.py               Chest 랩 이상 탐지·Tier 분류·길이 점프 탐지·SO 보간 함수
    RUN_fix_muscle_path_wrap_fail.py 랩 이상 탐지 → Tier별 복구 진입점
    rerun_freeze/
      RETRY_so_early_window.py       시작 직후 실패 → 0.05 s부터 SO·JR·BK 재실행
      RETRY_so_skipping_freeze_time.py  멈춘 프레임 건너뛰고 앞뒤 SO를 이어 붙임
    wrap_gapfill/
      DETECT_muscle_path_wrap_jump.py   SO 실패 트라이얼의 랩 이상 탐지·Tier 판정
      RETRY_so_gapfill_wrap_jump.py     Tier A 보간 복구
    wrap_fbp/
      wrap_fbp_lib.py                Tier B 트라이얼 모델 생성·SO 실행·기록
    diagnosis/
      RUN_quality_check_asymmetric.py   IK 마커 오차·ID 리저브·스케일링 점검
      RUN_compare_id_so_reserves.py     ID 모멘트 vs SO 리저브 힘 비교
      RUN_cross_so_freeze_quality.py    SO 멈춤과 품질 지표 교차
      RUN_cross_so_freeze_deeper.py     피험자 교란 제거한 멈춤 원인 분석
      RUN_scan_so_log_warnings.py       보존된 SO 로그의 근육·경로 경고 집계
```

이전 이름 → 현재 이름: `chest_wrap_lib` → `wrap_detect_lib`, `chest_wrap_tier_b` → `wrap_fbp_lib`, `run_chest_wrap_repair` → `RUN_fix_muscle_path_wrap_fail`, `retry_so_edge` → `RETRY_so_early_window`, `retry_so_freeze_skip` → `RETRY_so_skipping_freeze_time`, `detect_chest_wrap_anomalies` → `DETECT_muscle_path_wrap_jump`, `retry_so_path_gapfill` → `RETRY_so_gapfill_wrap_jump`, `update_pipeline_progress` → `UPDATE_pipeline_progress`, 진단 5개는 `RUN_` 접두. 진단 5개는 `d_Results_Analysis/`에서 옮김.

삭제(공식 코드로 흡수): `run_sub8_tier_b_fbp_all.py`, `run_sub8_tier_b_jr_all.py`, `run_sub8_mehf_missing_jr.py`.

## 4. 입력

- IK 결과 `<SUB>/<cond>/<AB|BC|CA>/IK/*_IK.mot`
- 공유 스케일 모델 `<SUB>/Model_osim/<SUB>_Scaled.osim`
- SO 실패 기록 `Analysis/Asymmetric/_diagnosis/pipeline_state/pipeline_trouble.json`
- 각 트라이얼의 SETUP_SO / SETUP_JR XML (공식 파이프라인이 생성)

## 5. 출력 위치와 이름

경로 함수는 모두 `Codes/PATH_RULE.py`에 있다 (`diagnosis_dir`, `pipeline_state_path`, `ConditionPaths.so_troubleshoot_dir / wrap_fbp_model_path / wrap_fbp_record_path / so_partial_path`).

### 5.1 정규 결과 (복구 여부와 무관하게 같은 위치)

`OpenSim_Process/_Main_/Asymmetric/<SUB>/<cond>/<AB|BC|CA>/SO_<app>/`, `JR_<app>/`

### 5.2 SO 결과 하위폴더 `SO_<app>/troubleshoot_so/<접근법>/`

| 접근법 | 파일 | 수명 |
|---|---|---|
| `wrap_fbp` | `<SUB>_<cond>_<seg>_<app>_WrapFBP.osim` (또는 `_ChestPatch.osim`) | 영구. SETUP_SO/JR의 `model_file`이 이 파일을 가리키고, 재실행 시 파이프라인이 자동 선택 |
| `wrap_fbp` | `<SUB>_<cond>_<seg>_<app>_wrap_fbp_record.json` | 영구. 바꾼 근육, 제외 구간, 이전 멈춤 시각, JR 여부 |
| `rerun_freeze` | `*.front.sto / *.back.sto / *.xml` 조각 | 실행 중에만. 이어 붙이기 성공 시 삭제, 실패 시 남김 |
| `wrap_gapfill` | 구간별 SO 조각 | 실행 중에만. 보간 결과 작성 후 삭제 |

### 5.3 `Analysis/Asymmetric/_diagnosis/`

| 하위폴더 | 내용 |
|---|---|
| `pipeline_state/` | 코드가 읽고 쓰는 상태 파일: `pipeline_progress.xlsx`, `pipeline_trouble.json`, `pipeline_freeze_sim_times.json` |
| `rerun_freeze/` | `pipeline_freeze_skip_report.json`, `code_freeze_audit.md`, `logs/` (재시도 실행 로그) |
| `wrap_gapfill/<SUB>/` | `chest_wrap_detect_report.json`, `chest_wrap_detect_flags.csv`, `wrap_repair_tier_a.json`, `wrap_repair_report_<stamp>.json` |
| `wrap_fbp/<SUB>/` | `wrap_repair_report_<stamp>.json`; SUB8은 `wrap_fbp_summary_reconstructed.json` |
| `quality_check/` | `quality_check_*.csv/.md`, `logs/` |
| `pipeline_runs/logs/` | `watch_gate_next_<namecode>.log` |

## 6. 실행 예시 (`Codes/c_Run_Tools`에서)

```text
python troubleshoot_so/RUN_fix_muscle_path_wrap_fail.py --from-trouble --namecode <CODE> --detect-only
python troubleshoot_so/RUN_fix_muscle_path_wrap_fail.py --from-trouble --namecode <CODE>
python troubleshoot_so/RUN_fix_muscle_path_wrap_fail.py --from-trouble --namecode <CODE> --apps MeasuredEHF --tier b-only
python troubleshoot_so/rerun_freeze/RETRY_so_skipping_freeze_time.py --namecode <CODE>
python troubleshoot_so/rerun_freeze/RETRY_so_early_window.py --namecode <CODE>
python run_opensim_pipeline.py --namecode <CODE> --tools jr --apps MeasuredEHF --skip-existing
python UPDATE_pipeline_progress.py
```

`--tier b-only`가 기존 SUB8 전용 스크립트를 대체한다. 이미 트라이얼 모델과 정규 SO 힘 파일이 있는 트라이얼은 `--rerun` 없이는 건너뛴다. 빠진 JR은 공식 파이프라인 `--skip-existing`으로 채우며, 이때 트라이얼 모델이 자동으로 쓰인다.

## 8. 이번 정리에서 생긴 문제

- SUB8 함수 경로 복구 배치 리포트 2개(`sub8_tier_b_fbp_all_report.json`, `sub8_tier_b_jr_all_report.json`)가 이동 중 잘못 삭제됨. 81개 트라이얼 기록과 요약(`wrap_fbp/SUB8/wrap_fbp_summary_reconstructed.json`)을 다시 만들었다.
- 2026-11-20 추가 복원: 각 `*_wrap_fbp_record.json`의 `length_rmse_m`을 공유 스케일 모델 + IK 정상 프레임으로 재적합해 채움(원래 콘솔 `[FBP] numpy … RMSE=`와 같은 정의; 근육값 324개, 중앙값 0.117 cm, 최대 0.209 cm). `so_wall_s_approx`는 트라이얼 모델→정규 force `.sto` 수정 시각 차(80/81, 중앙값 483 s). 적합 소요(`fit_s`)는 로그가 없어 복구 불가. 10AB는 이후 공식 파이프라인 재실행으로 force 시각이 바뀌어 `so_wall_s_approx`가 비어 있음.
- 기존 진단 출력은 재배치 후 진단 스크립트를 다시 실행해 현재 상태로 갱신됨.
- OpenSim 실행은 `C:\Users\ok\anaconda3\envs\osim\python.exe` 사용. 기본 `python`에는 `opensim`이 없어 SO가 실패하고, 이때 공식 파이프라인이 진행 시트를 그 피험자만으로 다시 써버린다(`refresh_progress_sheet([sub_n])`, 기존 동작). 그런 경우 `python UPDATE_pipeline_progress.py`로 전체를 다시 쓴다.

## 9. 검증 (2026-11-20)

- 실행 파일 13개 `--help` 정상, 라이브러리 import 정상.
- SUB8 15kg_10bpm 10AB MeasuredEHF를 공식 파이프라인으로 SO·JR 재실행: 트라이얼 모델(`_WrapFBP.osim`) 자동 선택, 결과가 기존과 완전히 같음 (SO force/activation, JR 최대 차이 0).
- 복구된 SUB8 트라이얼은 실패 기록에서 이미 빠져 있어 `RUN_fix_muscle_path_wrap_fail.py --from-trouble`로는 다시 잡히지 않음. 재실행은 공식 파이프라인으로 한다.
- 진행 시트 전체 갱신: 별도 파일로 만든 결과와 실행 시각 외 동일. SUB8 102/180, 실패 표시 30칸.
- SETUP: SO·JR 각 81개가 트라이얼 모델, 나머지는 공유 모델. 존재하지 않는 모델 경로 0 (IK SETUP의 빈 `model_file` 제외).
- 파일 개수: 트라이얼 모델 81, 기록 81, 정규 SO 81, 정규 JR 81. `troubleshoot_so/rerun_freeze` 조각은 보류분 3개만 남음.
